# Contributing

This guide covers how changes get into `main`. For setting up the project locally, see the
[README](README.md#quick-start) and [docs/OPERATIONS.md](docs/OPERATIONS.md).

## Workflow

1. Branch from `main`. Name the branch by type: `feat/…`, `fix/…`, `docs/…`, `chore/…`.
2. Make the change, with tests for any behaviour you add or fix.
3. Run the checks below before you push.
4. Open a pull request. Fill in the template, including how you tested the change.
5. CI must be green before merging.

## Checks

```bash
pnpm build
pnpm typecheck
pnpm test            # needs the Postgres test database; see the README
pnpm format:check
pnpm --filter @yohobed/web-extranet e2e   # browser tests, after a build and a seeded database
```

## Commit messages

Use [Conventional Commits](https://www.conventionalcommits.org/), with the area in brackets:

```
feat(stay-view): drag a booking to another room
fix(dashboard): open on the hotel's today, not the browser's
docs: record the Sprint 5 deploy
```

## Rules that keep the platform safe

- **Tenant data goes through `withTenant`.** Every new tenant table needs a row-level security
  policy. Add a test that proves one tenant cannot read another's rows.
- **Money rules live in `packages/domain`.** Keep pricing, tax and commission code free of
  framework imports, and cover it with unit tests.
- **Migrations are generated by Drizzle.** Never edit a migration that has been applied; add a
  new one.
- **Dates are the hotel's dates.** Use the property's time zone, never the browser's or UTC's
  "today".
- **No secrets in git.** Only `.env.example` files are committed.
